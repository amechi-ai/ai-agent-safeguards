# Security Response Agent — staged deployment

Status: proposed; no live credential, no live report read, no live message sent. The SRA is a deterministic Python process, not an LLM. The public repository holds source and synthetic tests only. Run the live workflow from a separate restricted private repository, not from public PRs. Do not supply credentials in chat, code, issues or public workflow logs.

## GitHub acknowledgement

The API supports listing triage advisories and creating an advisory comment; see https://docs.github.com/en/rest/security-advisories/repository-advisories?apiVersion=2026-03-10 . The fine-grained repository security advisories write permission is broader than comment-only authority. The implementation restricts its POST endpoint and fixed message; the underlying token itself is not a comment-only capability. A compromised runtime could misuse it. Prefer a separately isolated runtime with an independently enforced API proxy for stronger capability separation before wider deployment.

The prototype selects only triage submissions explicitly marked not accepted and not published/closed/withdrawn; rechecks before posting; avoids duplicate fixed acknowledgements by matching exact acknowledgement text and the independently configured, API-verified PAT actor (login and immutable numeric user ID); quarantines incomplete advisory comment lists while continuing other advisories and reports cycle failure for owner follow-up; refuses an incomplete advisory enumeration; limits writes to ten per cycle; follows no response URLs or redirects; prints generic success/failure only. The JSON API necessarily delivers untrusted report content to memory; the process does not interpret or execute it. No LLM, attachments, delegation, acceptance, triage changes, publication, external links, public comments, or report body retention. GitHub's advisory itself is the receipt/acknowledgement record; no public tracking store.

Limitations: no atomic read-and-post operation or idempotency key; duplicate replies remain possible if two runtimes operate simultaneously, a prior acknowledgement is edited/deleted, or a race occurs. The fixed message contains no report details. A state change after final read cannot be excluded. If pagination/shape changes, API errors, rate limits, or write cap occur, owner intervention is needed. Synthetic tests cannot establish live permissions or reporter visibility. No separate automatic owner notification is implemented; rely on GitHub security notifications and verify they are enabled. The 10-day response target is a separate owner policy decision.

## Activation checklist (owner only, after independent review)

1. Review and merge the source PR. Check synthetic CI and verify the checkout action pin independently. Create a private repository owned by the same account, e.g. ai-agent-safeguards-sra-runtime. Copy the exact reviewed sra/acknowledge.py and the template sra/private-workflow.yml.example to .github/workflows/sra.yml in that private repository. Protect main; restrict write access; do not enable PR-triggered jobs with secrets.
2. Create the sra-live environment; limit deployment branches to protected main only. Configure a short-lived fine-grained PAT under amechi-ai, access restricted to amechi-ai/ai-agent-safeguards ONLY, repository security advisories Read and write, required Metadata read only. No contents, administration or other write permission. Never send the token to the assistant. Store it as environment secret SRA_TOKEN in the PRIVATE runtime repository. Review whether API permissions and account identity are sufficient; stop if a broader grant is requested. Set SRA_ACTOR_LOGIN and SRA_ACTOR_ID from the independently verified user identity. Before reading reports, the script checks GET /user against both values and refuses on mismatch. Rotate/revoke promptly. GitHub App installation tokens are deliberately unsupported in this version; a separate reviewed implementation must verify their installation actor before adoption. A scoped proxy is an additional future improvement.
3. Initially leave repository variable SRA_ENABLED unset. Perform controlled integration testing with an explicitly authorised synthetic private vulnerability report, from a separate reporter account, and no real findings. Verify reporter sees exactly one fixed reply, repeat run adds none, no public disclosure, no report data in logs, and owner sees notifications. Before live enablement, ensure any test activation cannot touch actual reports (use a separate disposable target with reviewed target binding). The current hard-coded target must be changed and reviewed in that test copy; do not run live mode on the public target as a test. Provision a separate short-lived fine-grained test PAT scoped ONLY to the disposable target, using the same minimal permissions and its own isolated secret and environment; never reuse or widen the production PAT. Verify the test credential actor login and numeric ID independently, exercise repeat runs and mismatched-actor refusal, then revoke the test credential and remove the test secret before considering production activation. Stop/revoke if any deviation.
4. After independent acceptance and owner release, set SRA_ENABLED=yes and manually dispatch from main, then allow hourly schedule. Check run health daily, token expiry and notification settings; disable variable, workflow and revoke credential to stop. GitHub scheduled workflows can be delayed. Do not claim guaranteed response time. Only one live runtime.
5. Keep all findings and acknowledgements private. Never attach live response logs or report payloads to a public issue. Owner handles investigations, disclosure, status changes and escalation. Email remains manual until the separate channel passes integration checks.

## Masked iCloud email

Apple Hide My Email forwards to an underlying mailbox; do not grant the SRA access to a personal inbox. Apple Mail on Mac can reply using rules when open, but automated masked sender identity, recipient filtering, no quoted sensitive body, and loop prevention need verification before activation. Prefer a dedicated security mailbox with provider-supported server-side scoped auto-response, or a tested isolated mailbox integration. Do not configure a blanket personal-mail auto-reply. Confirm routing to the designated alias and test replies from unrelated external accounts, including auto-replies and duplicate messages. No email automation is deployed by this PR.
